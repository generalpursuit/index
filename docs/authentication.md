# Authentication and account isolation

Better Auth owns password hashing and signed sessions. [security-plugin.ts](../packages/auth/src/security-plugin.ts) adapts `/api/auth/security` endpoints to [security.ts](../packages/auth/src/security.ts) account operations. Endpoint details are available in the [auth OpenAPI document](api.md). Email codes prove ownership or authorize recovery; they never sign a user in. Built-in alternate verification/reset/change routes are blocked to preserve this contract.

## Sessions

Unverified accounts, including legacy accounts, receive restricted sessions. Get-session, sign-out and verification/correction remain available; application REST/RPC rejects the identity with HTTP 403 and `EMAIL_NOT_VERIFIED`, including otherwise-public reads. Anonymous reads retain normal visibility. Resolve current database session and verification state on API requests; cookie session caching is disabled. Idle clients do not run session-check timers. Live connections use one-use tickets minted after verified authentication, enforce their session expiry before sending hints, and close on committed session revocation. Hints carry no content; subsequent reads still authorize against current database state.

Native clients keep the signed **`set-auth-token` header**, replace it on rotation, and send it as a bearer credential. Never store the unsigned JSON token. Use API-scoped secure storage, erase credentials on expiry/sign-out, and follow the [shared Keychain contract](sharing.md#secure-hostextension-session-boundary) for extensions. Restricted sessions retain their credential while private content clears.

Verification/correction challenges belong to the requesting session. Address correction and account changes require the current password; the proven credential hash participates in the atomic update. Email stays unchanged until ownership is proven. Verification, password change and email change revoke other sessions; password reset verifies the address and revokes **all** sessions, then requires password sign-in. Reset responses do not reveal whether an address exists or delivery succeeded.

Codes expire, are single-use, and are stored as purpose/subject-bound HMACs. Database functions commit failed-guess accounting, challenge consumption, account changes and revocation atomically. Shared account/IP/recipient throttles apply across Workers. Preserve these functions when adding migrations. Auth traffic schedules bounded cleanup through Worker `waitUntil`; expiry checks never depend on cleanup.

## Account isolation

An account transition clears private queries, mutation state, drafts and navigation immediately. Async requests, parsed response bodies, token writes and success/rollback callbacks must still belong to the accepted account generation before publishing results. Transient refresh failures can preserve authorized cached data; forbidden/not-found responses must hide it. Device appearance is independent of account caches.

Pending native routes/clicks are recipient-bound. They may survive restricted-to-verified transitions for the same account, but must resolve against a fresh verified session before navigation or acknowledgement. Sign-out/account changes discard them. Desktop windows also obey the [native revision boundary](../apps/web/README.md#desktop-session-boundary).

## Delegated access for MCP clients

Better Auth's OAuth provider, configured by [mcp-authorization.ts](../packages/auth/src/mcp-authorization.ts), lets an MCP client act for an account. Its issuer is the stage's `/api/auth`, its one protected resource is the stage's `<API origin>/mcp`, and its consent page is the stage's web `/connect`; nothing names a host. Authorization-server and protected-resource metadata are served at the API origin's root, as RFC 8414 and RFC 9728 place them. [Agent tools](api.md#agent-tools) covers the endpoint and what agents may call. Discovery and the token, registration and revocation endpoints accept any origin without credentials; everything else keeps the explicit origin list.

There are two permissions. `read` reads everything the account can see through Index; `write` also acts as the account (save, edit, comment, forward). Every grant includes read, so write always means read + write. Every grant also includes `offline_access`, so its tokens can be refreshed: MCP clients ask for the scopes the protected resource lists, which leave it out, and their connections would otherwise end with the first access token. A connection lasts until it is disconnected. Consent shows the app's self-declared name and logo with the signed-in account, always grants read, and offers write when the app asked for it. Only a verified account can approve; restricted sessions go through the normal login and verification flow and return to the request. A client that forces login (`prompt=login`) gets a sign-in even when the browser is signed in: the login page sends the signed request with the sign-in, and Better Auth resumes it from the new session without the prompt. An account has one approval per app, enforced by a unique index; a re-approval, even one racing another, changes that approval's permissions in place. An existing approval covering the requested scopes is reused without asking again. No web page may be framed ([frame-protection.ts](../apps/web/frame-protection.ts) sends `frame-ancestors 'none'` and `X-Frame-Options: DENY` from the dev and preview servers and as the deployed `_headers` rules), so a framed consent page cannot collect a click.

Clients register with a Client ID Metadata Document (the MCP 2026-07-28 profile), or by unauthenticated Dynamic Client Registration as the fallback for older clients; registration is throttled per address. Metadata documents are fetched by [client-metadata-transport.ts](../packages/auth/src/client-metadata-transport.ts): HTTPS GET/HEAD only, redirects returned unfollowed, the caller's abort signal kept. Better Auth's Node transport pins DNS because a Node host can reach private networks. A Worker cannot: its subrequests leave through Cloudflare to the public Internet, IP-address URLs are refused and private networks need VPC bindings the API Worker doesn't have. Only same-zone requests could bypass Cloudflare to the zone's origin, which the API Worker's `global_fetch_strictly_public` compatibility flag prevents. Never run the transport on a host with private network access. Only staging and production accept metadata documents: Alchemy sets `CLIENT_METADATA_DOCUMENTS_ENABLED` to `true` for release stages alone, and local or personal stages, whose Worker can reach loopback and private addresses, offer dynamic registration only.

Authorization requires PKCE (S256). Tokens are Bearer tokens only: the MCP specification doesn't require DPoP, so discovery doesn't advertise it, registrations asking for DPoP-bound tokens and token requests carrying a DPoP proof are refused, a `dpop_jkt` authorization parameter is ignored, and `verifyMcpAccess` rejects any token with a key confirmation. Access tokens are opaque, prefixed and stored only as digests, bound to the `/mcp` resource (a request without a resource indicator is bound to it too) and expire after an hour; refresh tokens rotate, and presenting a rotated one outside a short retry window revokes the whole family. The MCP endpoint authorizes with `verifyMcpAccess` from `@index/auth`, which reads the database on every call: a token counts only while it is unexpired, issued for this stage's resource, its app is enabled, its account exists with a verified email and the approval it was issued under still exists. Its permissions are those of both the token and that approval. Each authorization code is bound to its approval's immutable ID as Better Auth stores it (`oauth_code_approval`, filled by a database trigger), and every token of the code, through each refresh, references that binding through the code ID Better Auth keeps. Deleting an approval therefore deletes its pending codes and all its tokens, an exchange or refresh already in flight cannot store new ones, and approving the app again starts a new approval under which nothing older counts. Disconnecting an app in Settings deletes its approval, so its next request fails; deleting the account cascades to its approvals. Password recovery disconnects every app: `index_auth_consume` deletes the account's approvals, with their codes and tokens, in the transaction that replaces the password and deletes the sessions. Approvals take turns with recovery on the account's user row and need a live session, so an approval, code, exchange or refresh racing recovery fails instead of surviving it. Signing out of the web does not disconnect apps: it ends the access tokens issued under that session, and the apps refresh, since their grants include `offline_access`.

## Delivery and checks

Configure server-only `RESEND_API_KEY`, a verified `AUTH_EMAIL_FROM`, and the explicit web origins in [deployment](deployment.md). `CORS_ORIGIN` is canonical; `AUTH_TRUSTED_ORIGINS` adds explicit HTTPS origins, with loopback HTTP allowed in development. The server and auth share that allowlist. Packaged Tauri origins are explicit; bearer requests need no browser Origin header.

Recovery delivery uses Worker `waitUntil` after its uniform response. Failed verification delivery leaves a restricted session and retry status; an older delayed message may contain a superseded code. No production code-reading endpoint or capture mode exists.

Run `bun test apps/server/src packages/api/src packages/auth/src apps/web/tests` from the root. The [browser checks](../apps/web/README.md#checks) use disposable auth fixtures. Before enabling real email delivery, check verified-sender delivery, delay/outage, recovery and revocation with isolated accounts. [Native checks](../apps/ios/README.md#checks) must also cover interrupted verification, offline sign-out and pending links across account changes.
