# Readable route contracts

Canonical paths are `/u/:username`, `/u/:username/:slug`, `/u/:username/favorites`, `/u/:username/starred`, `/l/:shortId`, and `/messages/:shortId`. `@index/api/routes` exports `profilePath(username)`, `groupPath(username, slug)`, `linkPath(shortId)` and `conversationPath(shortId)`. Builders return relative paths; clients use their configured web origin. UUIDs remain internal API identifiers.

Group create/update still accept `{name, visibility}`. Responses include `slug`. `normalizeGroupName` applies NFKC, collapses ASCII whitespace and trims ASCII spaces and edge byte-order marks (U+FEFF). Other invisible characters are retained in the display name. `groupSlug` lowercases ASCII A–Z only, replaces runs outside ASCII a–z/0–9 with a hyphen, strips edge hyphens, and uses `group` when empty. There is deliberately no locale-dependent transliteration or Unicode case expansion in slugs. For example, `İdea` becomes `dea`, while `FAVORİTES` becomes `favor-tes`; PostgreSQL and JavaScript use the same ASCII mapping. Display-name uniqueness uses PostgreSQL Unicode lowercase on the normalized name. All, Favorites, Starred and Settings slugs are reserved, including punctuation/compatibility variants. Display names are case-insensitively unique within an owner; slugs and their history are also unique within that owner. Conflicts return 409/CONFLICT.

The additive `20261010095101_readable_routes` migration preserves every record and UUID. System collections have priority; other groups are processed by creation timestamp then UUID. Duplicate normalized names/slugs and reserved custom names receive deterministic ` (2)`, ` (3)`, … suffixes (long names are shortened to fit). Read schemas preserve expanded legacy names without applying new input length limits (100 ligatures `ﬃ` become 300 letters `ffi`); create/rename inputs remain limited to 100 UTF-16 code units after normalization. Existing UUID URLs continue to identify the same group. Existing normalized usernames are retained; legacy null usernames receive `member_` plus 16 hex characters derived from the user ID, with a numeric collision suffix if needed.

PostgreSQL triggers reserve usernames on every user INSERT/username UPDATE, including Better Auth writes. `username_aliases(username PRIMARY KEY, user_id)` retains all historical names. A deleted user leaves a null tombstone, so a new account cannot take its old URLs. `group_aliases(owner_id, slug PRIMARY KEY, group_id)` has corresponding group deletion tombstones. The same identity can return to one of its own old names. Reservation uses an atomic UPSERT that locks the unique key, checks its owner, and raises SQLSTATE 23505 on conflict; the entire statement rolls back. This works with Neon HTTP without interactive transactions.

`@index/auth/namespace` exports `isUsernameAvailable(db, value, actorId?): Promise<boolean>` for advisory validation. It uses `usernameSchema`: trim, lowercase, 3–30 ASCII letters/digits/underscores. Auth writers send that normalized value; the existing database lowercase/trim constraint rejects unnormalized direct writes. A reservation is available only if absent or owned by the supplied actor. Do not treat this helper as the uniqueness guarantee. Registration/availability/update hooks give friendly reservation errors; concurrent losses are rejected by the database (Better Auth returns its creation failure; app profile/group mutations return CONFLICT).

Link and conversation responses include immutable 16-character URL-safe short IDs. A global permanent registry reserves randomly generated identifiers with bounded conflict retries. Database triggers assign IDs, refuse changes and preserve reservations after deletion; knowing one never grants access. The generated Drizzle snapshot describes tables/indexes; custom normalization functions/triggers and deterministic data repair live in the checked-in migration SQL and must be retained in future schema work.
