# Notifications

Index supports Messages, Comments, Mentions, Follow requests, New followers and Accepted requests. Preferences sync to the account; each device separately opts in. Categories default on and message/comment previews default off. Preferences never delete or disable in-app activity. No notification emails are sent.

Settings reports OS/browser permission separately from registration. Permission is requested only by **Enable on this device**. Denied permission remains denied; the app cannot override it. Unconfigured remote delivery and unsupported browsers are shown honestly. iOS Safari requires an installed Home Screen web app on a supported OS; the web manifest supplies an installable identity. The Tauri desktop uses native macOS alerts, independently of browser Push API support.

## Durable backend and privacy

Apply the checked-in `20261010103353_notification_delivery` and `20261010105457_notification_provider_tokens` migrations after the existing routing/auth migrations. They are additive and preserve those migrations' namespace/security functions and triggers. The integrated snapshot chain inserts `20261010104011_link_sharing` between the two notification migrations; apply all migrations in timestamp order. Do not use `db:push` in place of the migrations: the notification triggers and claim function are required. Database triggers insert notification events and per-device jobs in the same transaction as activity/message creation. A rollback leaves neither; message retry keys, source/recipient uniqueness and event/device uniqueness prevent duplicate jobs. Enrollment does not replay old events.

The Alchemy Worker has a one-minute Cron Trigger and exports `scheduled`. Postgres is the durable queue, so missed ticks, Worker termination and network failures retain work. A tick drains up to 200 jobs, using `FOR UPDATE SKIP LOCKED` claims and two-minute leases renewed before each delivery, with at most four provider requests at once. Retry delay starts at 15 seconds and doubles, respecting bounded Retry-After, up to eight attempts. Alerts older than 24 hours are discarded; event/job records are removed after seven days, without removing activity history. The process-owned macOS poller uses the same outbox with authenticated claim/ack every 15 seconds. Remote push latency can therefore be about a minute, and desktop latency about 15 seconds, plus provider/network time.

Every attempt and Web Push content resolution checks the subscription's still-existing, unexpired owning session, current verified account, current category/preview preferences, source existence, conversation membership or link/profile/group visibility, read state and active conversation. Forwarded link titles, URLs, images and descriptions are never included in alerts. The outbox stores references and status codes, never a body or serialized alert. Changes to private/locked content take effect before the next attempt. A notification already accepted/displayed by an OS cannot be recalled by a later privacy/preference change; logout clears local notifications where the platform permits it.

Web Push uses RFC 8291 aes128gcm encryption and RFC 8292 VAPID. Its encrypted payload contains only a job UUID. The worker fetches the current alert with the current session cookie, installation proof and expected session ID; stale accounts cannot display cached content. The worker has no offline content cache. It stores a bounded set of displayed IDs and uses notification tags to suppress retries. Clicks resolve again, then open same-origin readable routes, which recheck access. Some browsers may show their own generic background-update notice when their user-visible-push requirement applies to a discarded push; Index never falls back to private stale content.

APNs sends the currently permitted alert, short canonical path, recipient/job IDs and optional conversation ID. With previews off, its entire body is generic and there is no hidden message/comment text in other payload fields. APNs expiration is zero to avoid queueing stale private alerts for offline devices. Retry collapse IDs remain the job UUID. APNs provider JWTs are reused across cold Worker isolates via a private, 45-minute Postgres cache; raw signing keys remain server secrets. Dead tokens/endpoints are removed; credential/configuration failures retry without destroying registrations. Provider errors, endpoints, credentials and bodies are not logged. Delivery is at least once: provider acceptance and local display/ack cannot be one atomic transaction; collapse IDs and bounded native/worker dedupe reduce duplicates, without claiming exactly-once OS presentation.

Each installation has a random 256-bit proof, stored in browser IndexedDB or a separate native Keychain item; the server stores its SHA-256 digest. This proof is not a login credential: every device operation also requires a verified session and exact expected session ID. Enrollment can transfer an installation that proves possession; transfer clears its old jobs and active conversation. An unrelated installation cannot claim an existing endpoint. Subscriptions cascade on session deletion, and delivery/cleanup reject expired or newly restricted sessions. Device opt-out and signout clear local permission-registration state immediately and attempt server unsubscribe. Auth sign-out proceeds independently of a stalled notification removal request. Offline unsubscribe is best effort; local unsubscription/unregistration and session binding still guard the device. Old asynchronous callbacks cannot bind a newly signed-in account.

An active conversation is a 45-second per-device lease renewed every 15 seconds only while visible and focused/foregrounded. Reading a conversation suppresses redundant alerts to that device; other devices retain their own state. Losing focus/backgrounding clears it; a crash/offline transition can leave at most the lease duration of suppression. There are no permission prompts during restoration.

## Native background/lifecycle contract for menu-bar integration

`apps/web/src-tauri/src/notifications.rs` owns one runtime per application process. The Objective-C bridge in `native/notifications.m` handles UserNotifications, cookie-free/redirect-rejecting URLSession requests and a separate installation-proof Keychain item. All session reads use **`session::session_read()`**; its signature and existing API-scoped credential contract are preserved. Notification setup is an additive `notification_build.rs` hook. The native-smoke feature stubs notifications and never touches normal notification opt-in/proof state.

Commands exposed to the frontend:

- `notification_status()` reads actual permission and registration, resuming a previously opted-in account without prompting.
- `notification_start({ userId })` explicitly asks permission, verifies the fresh native session and enrolls this installation. It invalidates any prior runtime before starting one loop.
- `notification_stop({ preserveClick?: boolean })` synchronously invalidates generations, clears active/delivered state and local opt-in, then attempts authenticated removal. Explicit opt-out/signout clears pending clicks; account-boundary invalidation uses `preserveClick: true` to retain only the opaque, recipient-bound destination through verification.
- `notification_active({ conversationId: UUID | null })` updates the current window's active conversation. The native loop also checks native visibility/focus, so suspended webview JavaScript cannot keep a hidden conversation active.
- `notification_take_click({ ack?: id })` peeks at a canonical/account-bound click. Call with `ack` only after successful authorized navigation; a fresh native session check and the verified frontend both gate consumption. This works even before re-enrollment after a restricted session.

The menu-bar feature must retain this process/runtime when windows hide or close, call `notification_active(null)` when hiding the main window, and retain one runtime when opening another window. Explicit Quit ends the process and need not deliver. The OS click handler activates the app and shows an existing main window; when the menu-bar feature destroys/recreates windows, it must supply that recreation behavior and preserve the pending click. Reuse DesktopTheme on every new window. This feature does not change close/quit policy or implement a menu bar.

iOS registers through UIApplication and UNUserNotificationCenter only after opt-in; APNs token callbacks are generation/account guarded. Notification clicks enter `AppModel.open` / `resumeReadableURL`, retaining `pendingRouteURL` and its recipient through restricted same-ID verification until authorized resolution succeeds. Session credential storage is unchanged. The isolated `NotificationInstallation` Keychain service is `com.generalpursuit.index.notifications.<API scope>`, account `installation`, WhenUnlockedThisDeviceOnly. Sharing's later shared-Keychain migration must preserve this independent item, combine its Keychain entitlement with the APS entry, and compose both source-generation/build hooks. APIClient's immutable public baseURL is explicitly nonisolated for reading this scope.

## Configuration (not provisioned here)

Keep all private values in the deployment secret store. The browser receives only the VAPID public key and availability, through the verified notification API.

| Server input                  | Purpose                                                                                                                |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `NOTIFICATIONS_ENABLED=true`  | Enable remote APNs/Web Push processing and enrollment; native desktop poll delivery does not require push credentials. |
| `VAPID_PUBLIC_KEY`            | URL-safe unpadded base64, uncompressed P-256 public key (65 bytes).                                                    |
| `VAPID_PRIVATE_KEY`           | URL-safe unpadded base64 P-256 private scalar (32 bytes).                                                              |
| `VAPID_SUBJECT`               | Operator `mailto:` or HTTPS contact. This is not an email notification sender.                                         |
| `APNS_KEY_ID`, `APNS_TEAM_ID` | Apple-issued signing-key and team identifiers.                                                                         |
| `APNS_PRIVATE_KEY`            | Full PKCS#8 `.p8` signing key PEM.                                                                                     |
| `APNS_TOPIC`                  | Provisioned application bundle identifier; checked-in iOS identifier is `com.generalpursuit.index`.                    |
| `APNS_ENVIRONMENT`            | `sandbox` or `production`, matching the signed app's entitlement; mismatches are rejected at enrollment.               |

Generate one VAPID P-256 ECDSA pair using an audited key-generation tool (Node/WebCrypto can export public raw key and private JWK `d`); retain the pair across deployments. Never put a private key in a `VITE_` variable, app bundle, source tree, log or notification payload. Changing VAPID keys requires re-enrollment of browser subscriptions. APNs key rotation changes the private provider-cache key automatically. Protect the provider-token database table as credentials; its entries expire and are swept by the worker.

Web subscription URLs are restricted to HTTPS known push-provider hosts (FCM, Mozilla, Apple and Windows) and no redirects. Add a reviewed exact provider domain to `endpoints.ts` for another supported provider; never enable arbitrary user-selected fetch URLs.

Use deployment/auth trusted origins for canonical and alias web domains and their CORS/cookie relationship to the API. Native readable routes use configurable `INDEX_WEB_URL` and `INDEX_WEB_ALIASES`. `i.generalpursuit.dev`, `index.generalpursuit.dev` and any later dedicated domain remain choices, not deployed assumptions. Notification paths are relative to the configured web origin. The proposed `accounts@auth.generalpursuit.dev` belongs only to authentication email configuration; notifications do not use it.
