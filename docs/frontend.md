# Web application

The production entry point is `/`.

## Structure

- `apps/web/src/routes/_app`: file routes, validated URL state, authentication guards, and query-backed loaders.
- `src/features/<feature>/hooks`: account-scoped oRPC/TanStack Query queries, pagination, and mutations. Routes and components share cache keys.
- `src/features`: feed, link library, profiles/connections, discovery, activity, and messaging.
- `src/hooks`: small shared hooks for account access, local drafts, debouncing, and history/edge navigation.
- `src/components/app`: navigation and application-level compositions of the shared shadcn Base UI primitives.
- `src/app.css`: responsive application layouts and visual styling. Reusable primitives remain in `packages/ui`.

The weekly feed shows one viewport-sized week and changes week only on purpose: through the week scrubber on the right edge (the same one as on profiles) or the list of weeks behind the week title. Scrolling never changes the week, so reaching the end of a list stays put. A neighboring week slides into place before the URL updates; farther weeks open directly. Adjacent weeks are prefetched, with only the active week available to keyboard and assistive-technology navigation. Weeks without links from you or your people are skipped. The stationary header shows the selected week number in Source Serif 4 Display bold and updates after scrolling settles. Only the content beneath it scrolls; each week shows your links above your people's, without visible section labels (screen readers still get them). Every row's marker column is as wide as an avatar, so markers center under people and titles start where their names do. The friends carousel scrolls horizontally (swipe, trackpad or arrow keys); with a mouse, clicking the dimmed box peeking in at either edge brings it into view instead of opening what is half hidden in it. There are no carousel arrows. More people load as the end of the carousel comes near (a button appears only to retry a failed load). An empty current week shows just the “Enter a link” field; past weeks say “Nothing saved this week.” When nobody you follow shared anything, a bordered box the size of a person's column holds a centered message: “Find people whose taste you trust” with a Discover link, or “Nothing shared this week yet” once you follow people. Links show a colored marker for their server-assigned category instead of an icon. A row's title opens the post and its domain opens the website; favorites, forwarding, editing and deleting live in the post view. A profile shows the avatar, name and one line of facts, with Settings (including profile visibility, groups and sign-out) in the navigation rail on larger screens and behind the profile's gear on phones. Below it, the person's links are one continuous list of weeks. Each week's serif title (with its dates as a small label) sticks at the top while you read that week, and a list menu rides at the end of that sticky row: All, Favorites and the person's groups, then — on your own profile only — Starred (other people's links you kept, each row naming whose it is) and “New group”. A week loads its links when it comes near the screen and holds their space until then, so jumps land exactly. The list leaves just enough empty space after its last week for that week's heading to reach the top, so every week can be jumped to and read under its sticky title. A scrubber on the right edge, starting level with the top of the list (where scroll position is expected, apart from the navigation rail; on phones in its own lane beside the rows) has one tick per week (the week you are reading drawn longer); hovering — or pressing and sliding on touch screens, where letting go jumps to the named week — names a week in one label that keeps the size of the longest week and dates on that profile, so it never jumps, and opens into the gutter when it fits (otherwise over the end of the rows); clicking jumps there. Tapping a week title opens the same choice as a list of weeks with their link counts, for keyboards, screen readers and phones. On your own profile, links in a locked group show a lock in All. Groups are managed in Settings (create, lock any list, rename or delete your own groups); the profile only shows and filters them. Weeks follow the date a link was saved, for every list. Menus (the profile's list menu, link actions, group actions) share one quiet style: a rounded near-black panel, soft grey rows that brighten on hover, a leading slot so labels align whether or not they have an icon, a small white square for the chosen option, thin inset dividers, and destructive actions that turn red only when pointed at; their triggers have no box and brighten while open. Modals are one shared component: a centered dialog on larger screens and a swipeable bottom sheet on phones (Base UI Drawer), with serif titles and one primary action in a footer; confirmations stay small centered dialogs. The current week starts with an “Enter a link” field that stays in place above your scrolling links: pasting a link, or typing one and pressing Enter, saves it immediately. The server reads its title and category; until then a pending row with an outlined marker shows, and it turns into the saved row in place. The confirmation offers Undo. This field is the only way to add a link, on phones too (where its input keeps 16px text so focusing it does not zoom); your profile shows it as well, adding into the selected group. There is no add button or add modal. Editing a link (from the post view's actions) opens a modal over the current page via the `edit` search parameter, next to the `post` parameter, with the link's address, title, note and a group choice that says who will see the link; a new address has its category read again. Links without a group follow the profile's visibility; only locked groups hide links further. Each week splits into two fixed zones, your links on top and your people below, so both sit in the same place every week whatever their length; each zone scrolls internally when full. Scrollbars are hidden: a list fades out on any edge with more content behind it, and in the carousel the box peeking in (less than 90% in view) is dimmed, so boxes in view never fade. The carousel always comes to rest on a whole box. Link lists show only whole rows and stop on a row, so the gap under the field never changes and the row at a faded edge is dimmed. A week's list loads its next page as you near the end (a button appears only to retry a failed load), and adding a link scrolls the list back to the top: at once when saving from the field, so its pending row and then the saved link are in view, and on arrival for links added elsewhere, such as another device. Friends appear as two columns of the same rows, one full-height column per person. With more than two people the columns narrow so the next one peeks in, dimmed, as the way to the next person. Large collections scroll within their own list. Every page of links, people, activity, and messages remains accessible through pagination.

URL state holds the selected week, profile group, discovery query, activity filter, and open post. Account-specific API keys prevent sharing cached private results between accounts; sign-out clears queries and drafts. Drafts survive internal navigation in memory and are discarded on reload or account changes.

Discover and Messages share one outlined search field (same size, inset and text position) and the same empty line. People in Discover show who you follow that follows them (“Followed by lena”, “lena and amir”, or “lena and 2 others”), worded like the line on a profile. Empty results are a single centered, muted line; only the home page's people placeholder is a box. Activity uses the same display typography as the weekly feed and Discover. Its filters are All, Comments, Requests, Mentions and Follows; acceptance events remain in All. Typing `@username` in a comment notifies readers who can access that post, and the notification opens the original thread.

On larger screens Settings sits at the foot of the navigation rail and opens `/settings` as a page without a back button. On phones the gear on your own profile opens Settings as a bottom sheet over the profile (via the profile's `settings` search parameter), closed with ✕ or by swiping down; long sheet content scrolls inside the sheet. Settings is a column of boxes: who you are (avatar, name and username; the avatar picks a new photo and ✎ opens an Edit profile modal with photo, name and username saved together), profile visibility (a quiet menu, behind a confirmation), Groups (a + to create one, then each list with its link count, lock and, for your own groups, rename/delete) and a full-width Sign out. Picked photos are cropped to their centre square and shrunk to 512×512 WebP in the browser before upload. Saves retain input on failure and refresh profile/session data on success; navigation and profile lists do not expose a separate sign-out action. The SwiftUI client uses the same Settings entry.

Forms use TanStack Form with the API's Zod field schemas. Dialogs, menus, select controls, tabs, and avatars use official shadcn Base UI components. Privacy changes require an explicit confirmation dialog. Request errors retain input and provide retry feedback.

Messaging uses exact participant sets for unnamed groups. Selecting recipients queues an attachment in the conversation composer; only pressing Send transmits it. A stable client UUID protects retries. Restricted original posts expose only the original author's public identity. See [API policy](api.md#direct-and-group-messages).

Messages poll every 5 seconds, conversation lists every 10 seconds, and activity every 30 seconds while the app is foregrounded. There is no push or websocket dependency.

## Loading and refresh

Feature query options are shared by route loaders and hooks. Navigation intent preloads the first screen of activity, conversations, profiles, and settings; discovery preloads suggestions while typed searches remain debounced. Conversation headers and messages load together. Cached data stays available for 30 minutes of inactivity, remains fresh for 30 seconds, and refreshes in the background. Session revalidation does not block navigation when a session is already known. Account-specific keys and sign-out clearing still isolate readers.

Opening a visible post seeds its detail from the row and immediately revalidates access; author and comments are prefetched on pointer/focus/touch intent. Profile weeks render as each index page arrives, with failed pagination offering retry. Recoverable background failures keep known content visible with a retry notice; authorization and not-found errors hide it. Successful link edits and message sends update the relevant detail cache directly, and Favorites/Stars update optimistically with rollback. Discovery supplies follow status instead of fetching a full profile for every row.

These changes also apply to the bundled Tauri frontend. The app remains a client-rendered application using the shared API, without an additional rendering server or persistent browser data cache.

The browser performance tests hold requests open to verify that known content renders before a refresh finishes, and count prefetch/profile requests. To run a second isolated test stack alongside development, set `E2E_API_PORT=3102 E2E_WEB_PORT=4273` when invoking Playwright; the defaults remain 3002 and 4173. For production-bundle verification, first build with the matching `VITE_SERVER_URL` and then run Playwright with `E2E_PRODUCTION=1`.

## Run and check

Use the root development workflow for the actual application/backend and apply the checked-in database migrations through the existing deployment workflow.

```sh
bun run check-types
bun test packages/api/src apps/server/src
cd apps/web
bun run test:e2e
```

Install Playwright's browser once with `bun x --no-install playwright install chromium`.

Playwright starts Vite on port 4173 and a disposable PostgreSQL/PGlite API on port 3002, with real Better Auth and oRPC handlers. It does not read production database credentials or write to the live database. Each test recreates its own fixture data. Coverage includes desktop/mobile layouts, weekly navigation, links/Favorites, profile privacy and follow requests, group management, comment actions, restricted forwards, replies, failed-send recovery, registration, and sign-out isolation.

The test API is a loopback-only test entry point; it is not imported by the application or deployed server. Browser traces and screenshots go to ignored `apps/web/test-results`.
