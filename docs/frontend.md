# Web application

The production entry point is `/`.

## Structure

- `apps/web/src/routes/_app`: file routes, validated URL state, authentication guards, and query-backed loaders.
- `src/features/<feature>/hooks`: account-scoped oRPC/TanStack Query queries, pagination, and mutations. Routes and components share cache keys.
- `src/features`: feed, link library, profiles/connections, discovery, activity, and messaging.
- `src/hooks`: small shared hooks for account access, local drafts, debouncing, and history/edge navigation.
- `src/components/app`: navigation and application-level compositions of the shared shadcn Base UI primitives.
- `src/app.css`: responsive application layouts and visual styling. Reusable primitives remain in `packages/ui`.

The weekly feed settles on one viewport-sized week. Native vertical scrolling reveals the adjacent week and snaps into place when the gesture ends; the URL updates only after settling. Adjacent weeks are prefetched, with only the active week available to keyboard and assistive-technology navigation. Weeks without links from you or your people are skipped. The stationary header shows the selected week number in Source Serif 4 Display bold and updates after scrolling settles. Only the content beneath it scrolls; each week shows your links above your people's, without visible section labels (screen readers still get them). Every row's marker column is as wide as an avatar, so markers center under people and titles start where their names do. The friends carousel scrolls horizontally; its arrows, like the newer-week arrow, appear only when there is somewhere to go. An empty current week shows just the “Enter a link” field; past weeks say “Nothing saved this week.” When nobody you follow shared anything, a bordered box the size of a person's column holds a centered message: “Find people whose taste you trust” with a Discover link, or “Nothing shared this week yet” once you follow people. Links show a colored marker for their server-assigned category instead of an icon. A row's title opens the post and its domain opens the website; favorites, forwarding, editing and deleting live in the post view. A profile shows the avatar, name and one line of facts, with Settings (including profile visibility and sign-out) behind the gear. Below it, the person's links are one continuous list of weeks. Each week's serif title (with its dates as a small label) sticks at the top while you read that week, and a list menu rides at the end of that sticky row: All, Favorites and the person's groups, then — on your own profile only — Starred (other people's links you kept, each row naming whose it is) and “New group”. A week loads its links when it comes near the screen and holds their space until then, so jumps land exactly. The list leaves just enough empty space after its last week for that week's heading to reach the top, so every week can be jumped to and read under its sticky title. On wide screens a scrubber in the right gutter (where scroll position is expected, apart from the navigation rail) has one tick per week (the week you are reading drawn longer); hovering names a week in one label that keeps the size of the longest week and dates on that profile, so it never jumps, and opens into the gutter when it fits (otherwise over the end of the rows); clicking jumps there. Tapping a week title opens the same choice as a list of weeks with their link counts, for keyboards, screen readers and phones. On your own profile, links in a locked group show a lock in All. Groups are managed in Settings (create, lock any list, rename or delete your own groups); the profile only shows and filters them. Weeks follow the date a link was saved, for every list. Modals are one shared component: a centered dialog on larger screens and a swipeable bottom sheet on phones (Base UI Drawer), with serif titles and one primary action in a footer; confirmations stay small centered dialogs. The current week starts with an “Enter a link” field that stays in place above your scrolling links: pasting a link, or typing one and pressing Enter, saves it immediately. The server reads its title and category; until then a pending row with an outlined marker shows, and it turns into the saved row in place. The confirmation offers Undo. This field is the only way to add a link, on phones too (where its input keeps 16px text so focusing it does not zoom); your profile shows it as well, adding into the selected group. There is no add button or add modal. Editing a link (from the post view's actions) opens a modal over the current page via the `edit` search parameter, next to the `post` parameter, with the link's address, title, note and a group choice that says who will see the link; a new address has its category read again. Links without a group follow the profile's visibility; only locked groups hide links further. Each week splits into two fixed zones, your links on top and your people below, so both sit in the same place every week whatever their length; each zone scrolls internally when full. Scrollbars are hidden: a list fades out on any edge with more content behind it, and in the carousel the box peeking in (less than 90% in view) is dimmed, so boxes in view never fade. The carousel always comes to rest on a whole box. Link lists show only whole rows and stop on a row, so the gap under the field never changes and the row at a faded edge is dimmed. A week's list loads its next page as you near the end (a button appears only to retry a failed load), and adding a link scrolls the list back to the top: at once when saving from the field, so its pending row and then the saved link are in view, and on arrival for links added elsewhere, such as another device. Friends appear as two columns of the same rows, one full-height column per person. With more than two people the columns narrow so the next one peeks in, and the carousel arrows sit on the faded left and right edges, level with the people's names. Phones show the fades without arrows and are swiped. Large collections scroll within their own list, then allow week navigation at the boundary. Every page of links, people, activity, and messages remains accessible through pagination.

URL state holds the selected week, profile group, discovery query, activity filter, and open post. Account-specific API keys prevent sharing cached private results between accounts; sign-out clears queries and drafts. Drafts survive internal navigation in memory and are discarded on reload or account changes.

Discover and Messages share one outlined search field (same size, inset and text position) and the same empty line. People in Discover show who you follow that follows them (“Followed by lena”, “lena and amir”, or “lena and 2 others”), worded like the line on a profile. Empty results are a single centered, muted line; only the home page's people placeholder is a box. Activity uses the same display typography as the weekly feed and Discover. Its filters are All, Comments, Requests, Mentions and Follows; acceptance events remain in All. Typing `@username` in a comment notifies readers who can access that post, and the notification opens the original thread.

Your own profile’s gear opens `/settings` on desktop and mobile. Settings owns name, username, image URL (with preview and removal), and sign out; navigation and profile lists do not expose a separate sign-out action. Saves retain input on failure and refresh profile/session data on success. The SwiftUI client uses the same Settings entry.

Forms use TanStack Form with the API's Zod field schemas. Dialogs, menus, select controls, tabs, and avatars use official shadcn Base UI components. Privacy changes require an explicit confirmation dialog. Request errors retain input and provide retry feedback.

Messaging uses exact participant sets for unnamed groups. Selecting recipients queues an attachment in the conversation composer; only pressing Send transmits it. A stable client UUID protects retries. Restricted original posts expose only the original author's public identity. See [API policy](api.md#direct-and-group-messages).

Messages poll every 5 seconds, conversation lists every 10 seconds, and activity every 30 seconds while the app is foregrounded. There is no push or websocket dependency.

## Run and check

Use the root development workflow for the actual application/backend and apply the checked-in database migrations through the existing deployment workflow.

```sh
bun run check-types
bun test packages/api/src apps/server/src
cd apps/web
bun run test:e2e
```

Install Playwright's browser once with `bun x --no-install playwright install chromium`.

Playwright starts Vite on port 4173 and a disposable PostgreSQL/PGlite API on port 3002, with real Better Auth and oRPC handlers. It does not read production database credentials or write to the live database. Each test recreates its own fixture data. Coverage includes desktop/mobile layouts, weekly navigation, links/Favorites, profile privacy and follow requests, group management, comment actions, restricted forwards, replies, failed-send recovery, registration, and sign-out isolation.

The test API is a loopback-only test entry point; it is not imported by the application or deployed server. Browser traces and screenshots go to ignored `apps/web/test-results`.
