# macOS menu bar

Index for macOS adds a template status icon to the system menu bar. macOS controls its position among the other status items. Clicking it opens a compact 420×560-point window, clamped to the status item's screen. Click again, press Escape outside an open picker/dialog, click the close button, or move focus away to hide it.

The panel shows **the current UTC week's own links**, including owned private groups; it does not show followed people's links or earlier weeks. Its list paginates and updates across the UTC Monday boundary. It reuses the main app's `QuickAdd`, `DestinationPicker`, `useDestinationStatus`, `useShareSave`, and Monday/week formatting. Paste or Enter saves into Your links or the selected owned group. Group creation selects the full returned Group. Rename/privacy changes refresh the selection; confirmed deletion leaves an unavailable destination until the user explicitly chooses another one. Uncertain saves retain their retry receipt and input across ordinary hide/reopen. Duplicate detection offers **View existing** in main or explicit **Save again** with a new operation ID.

Saved rows recheck access before opening their current HTTP(S) URL through the existing validated native opener. **View existing** queues only a short relative path and recipient identity for the main window, which freshly resolves canonical access before navigation and acknowledgement. Restricted sessions retain the opaque queue through same-ID verification. A different account cannot consume it. Remote WebView navigation and popup restrictions apply equally to both windows.

**Open Index** restores/unminimizes the main window, recreating it if necessary. Closing main hides it and clears active-conversation presence; the menu bar and the existing native notification runtime keep running. Closing/hiding the panel does not own notification presence or delivery. **Quit** and Command-Q exit the process. Quitting retains device notification opt-in for the next launch. Notification clicks specifically show/create main, never whichever key-capable window happens to be first. There is no second poller or login helper process.

## Launch at login

Launch at login starts **off on a new installation**: startup and status reads never register a login item. A user's prior OS choice remains authoritative. The checkbox reads `SMAppService.mainAppService.status` on mount and focus, and changes it only on an explicit user action. Enabled, off, approval required, missing app, unsupported OS/build and operation failures remain distinct. Approval required stays unchecked, with Open Login Items and Cancel request. Registration failures never optimistically show enabled. No browser preference mirrors the OS state. Notification opt-in and Launch at login are independent.

ServiceManagement requires a packaged app on macOS 13 or later; current signed sharing builds have their own documented deployment-target requirements. Older/unpackaged builds report unsupported. An enabled login item launches the same Index application with its main window and menu icon; it does not start a second background executable. A per-user advisory lock under the bundle's Application Support directory prevents simultaneous duplicate processes, with a content-free distributed notification to show the existing main window. The lock has no credentials, is not deleted while running and is released by the OS on exit/crash. Native smoke builds keep their existing isolated session behavior and omit the status item/login item.

## Account, cache and window boundary

The secure session remains API scoped in `session.rs`. The shared Keychain namespace, normalization, read-only Share extensions, error behavior and deliberate one-time sign-in transition are unchanged. The legacy `session_read()` and `session_write(token)` commands remain; new webviews use:

- `session_snapshot()` → `{ token, revision }`, read under the same process lock as writes.
- `session_compare_write({ token, expectedRevision })` → new revision. A stale writer cannot erase/restore another window's credential. Null writes synchronously invalidate native delivery before erasing storage, including offline sign-out.
- `session_revision()` → current revision; no token.
- `session_touch({ expectedRevision, invalidateNotifications? })` advances access state without replacing a credential. Same-token verification changes reach peers. Actual loss of verified access invalidates delivery while retaining the recipient-bound opaque click.

Normal API requests, including Sign out, bind to the revision their window accepted through `sessionOptions`, after identity/generation checks and cache cancellation. They **cannot adopt the newest credential at request start**: if a hidden window missed an account event, its old draft is rejected before any network mutation, then its identity, drafts, queries and late callbacks are cleared and revalidated. Get-session and intentional password sign-in are explicit refresh paths. Requests also check the native revision after the complete response body, before accepting results or writing rotated credentials. Local writes remain serialized, with process-wide compare-and-set ordering for the two webviews.

Sign-out captures the old bearer for best-effort server revocation, CAS-erases the local credential, and clears/navigates the issuing window immediately **before waiting for the auth request or response body**. Peer events clear the other window. Stalled auth or notification removal cannot keep local content usable; an old completion cannot erase or navigate a subsequent account. Failed secure-storage erasure remains an error, not a claim of successful sign-out.

Only `{ revision, source }` travels in native session/data events: no token, profile, link, query data or draft. Successful mutations invalidate peer account-scoped queries; focus also revalidates, covering missed events. Each webview keeps the existing query keys and account-generation guards. Hidden panel reopening waits for the session/UI to accept a current revision before native presentation, and credential/access changes hide the old panel. No credential is written to Web Storage or an event. Both windows install the existing `index.theme` store and `DesktopTheme`; device appearance stays independent of account clearing.

Only main mounts `NotificationLifecycle`. All window-origin notification commands carry `expectedRevision` from the window's accepted binding, including asynchronous effect cleanup. Native status/start/stop/active/click operations reject stale revisions; state changes run under the session lock before the notification-runtime lock. Start validates the requested verified user before replacing a runtime and checks again when installing the registration. Native hide/quit/session cleanup retains its internal entry points. Terminal worker cleanup validates and invalidates its generation under one runtime lock. Every generation transition also invalidates the OS display epoch. Display work captures that epoch while its generation is current, before queueing a blocking job, and passes it to Objective-C. Delayed jobs cannot adopt a newer account's epoch; stale completions only remove their own notification ID. Display submission and seen-ID updates are serialized with native clear. See the updated [notification contract](notifications.md#native-backgroundlifecycle-contract-for-menu-bar-integration).

## VM verification

Use isolated fixtures and ports. This rollout uses API 3802, web 4973 and owned Xvfb 178; no live accounts/databases, production credentials or services are used. From the repository root:

```sh
export PATH=/home/ono/.npm/_npx/22f2fe8d8bc13000/node_modules/.bin:$PATH
bun test packages/api/src apps/server/src apps/web/tests packages/infra
python3 apps/web/scripts/check-menu-bar-source.py
python3 apps/ios/Scripts/check-sharing-source.py
python3 apps/web/scripts/test-share-profiles.py
VITE_SERVER_URL=http://localhost:3802 bun run --cwd apps/web check-types
E2E_PRODUCTION=1 python3 /home/ono/index/.git/t3-feature-rollout/run-browser-tests.py \
  --feature menubar -- menu-bar.spec.ts desktop.spec.ts notifications.spec.ts \
  sharing.spec.ts groups.spec.ts security.spec.ts settings.spec.ts readable-routes.spec.ts
```

The VM-only runner owns and cleans its Xvfb/API/preview/Chromium processes. Elsewhere use the equivalent Playwright commands with disposable ports. Browser tests exercise real React/Query/Router/auth/API data against PGlite with two pages and a shared, in-memory desktop IPC fixture. The fixture proves bridge calls and frontend boundaries; it does **not** execute Tauri, AppKit, Keychain, ServiceManagement or OS notifications. Source/config checks inspect build composition, local navigation/capabilities, reproducible vector assets, command guards and native lifecycle ownership. They do not compile native code.

Transport tests cover delayed private/null-session bodies, held credential writes, CAS rejection, missed peer events followed by a stale draft or logout, explicit session acceptance and prompt local erasure with held auth network/body. Browser cases cover compact group creation/focus, current-week isolation, duplicate saves/canonical main routing, cross-window refresh and themes, unverified-to-verified transitions, account changes/draft removal, lost events, stalled sign-out, held native-command contracts, receipt retention, deleted destinations and OS-state-driven login-item UI. Checked-in Rust tests cover revision guards, native path validation/login-status mapping, hide-preserves-runtime, shutdown-ends-runtime, and delayed old display/worker termination after a new runtime starts; these require the Mac toolchain below.

Recorded on this Linux worktree (2026-10-10): **179/179 Bun tests across 39 files**, **40/40 production headed browser cases** (eight menu-bar cases plus the existing 32), **6/6 menu-bar source/config checks**, **4/4 sharing source checks**, and **7/7 synthetic signing-profile checks** passed. ## Required Mac verification

No Rust/Objective-C/Swift build, native app launch, signing, ServiceManagement registration, real Keychain access or real notification delivery was performed on this Linux VM. Older Mac evidence in `desktop.md` predates this feature. On the user's Mac with full Xcode, first use disposable credentials/API data and run:

```sh
cd apps/web/src-tauri
VITE_SERVER_URL=http://localhost:3802 cargo test --locked
# Includes the session revision and notification lifecycle unit tests.
```

Then build the real bundle using [desktop packaging](desktop.md#packaging) and [sharing's signing/profile instructions](sharing.md#tauri-macos-packaging). Choose real deployment inputs; the example endpoint here is disposable, and a remote Mac must be given an appropriately reachable test API. A host-only local shell build can use `bun run desktop:build --local --without-share-extension --bundles app`; it does not verify the extension. Do not treat the opt-in `native-smoke` build as evidence for the menu bar, because it deliberately disables the menu lifecycle.

1. **Build/package:** compile the locked Rust code and both Objective-C bridges with Xcode; inspect the final host/share extension signatures, profiles, entitlement scopes and embedded extension. Install the signed app in Applications. Confirm one template status icon with accessible name, normal default-browser dispatch, and blocked `file:`, credential-bearing, remote navigation and popup URLs in both webviews. Test configured canonical/alias domains rather than hardcoding `i.generalpursuit.dev`, `index.generalpursuit.dev` or a future domain.
2. **Placement/focus:** test menu-bar auto-hide, notch, main/secondary displays, different scaling, moved status item, docks on different edges, Spaces/fullscreen, short screens and sleep/wake. Check panel clamps below its actual status item; first open can load a hidden WKWebView and reveal promptly, including offline/session-error states. Test repeat click, outside click, Escape, Command-W, group/duplicate dialogs, stable trigger focus, keyboard navigation and VoiceOver. Inspect both light/dark first paint and native chrome.
3. **Lifecycle/single instance:** close main using the red button and Command-W; verify the process and icon stay alive and the main conversation stops suppressing alerts. Open Index and Dock reopen must restore main; forced main-window destruction followed by a notification/open action must recreate it. Repeated clicks and simultaneous duplicate launches must keep one process/icon/poller. Hide/destroy panel while main is reading a conversation and verify it does not clear main's state. Quit from the panel, app menu and Command-Q must actually exit; a new launch retains user opt-in.
4. **Session races/Keychain:** with two disposable accounts, hold a response/body and credential write, sign out/switch accounts in main, and attempt an old draft, Undo, View existing, sign-out and notification command in a stalled panel. No operation may run under the new account. Verify both windows promptly clear with auth and notification removal offline/held. Confirm restricted sessions expose no app data and same-ID verification resumes permitted opaque destinations. Lock/unlock Keychain, reject an access prompt, revoke the session and repeat restore/sign-out. Confirm the shared extension still reads the same API-scoped credential and never gets a fallback legacy credential.
5. **Launch at login:** verify a clean install is off and merely opening the panel never registers. Enable, exercise approval required, approve/deny/revoke in System Settings, return focus and confirm the actual checkbox/status. Cancel an approval request and disable again; log out/in to test both choices. Test a moved/missing bundle and an unpackaged development run. Check macOS release signing/notarization requirements with the actual chosen identity; no login helper/profile/credential was provisioned here.
6. **Real notifications:** enable the existing native runtime with a verified disposable account. Hide/close main and send a real permitted event; ensure one delivery. Click while panel is visible, main is hidden, and main must be recreated: main must open, resolve current recipient/access, and only then acknowledge. Repeat denied/revoked permission, account switch, restricted verification, sleep/wake and network outage. A delayed old start/stop/active/ack must not alter a newer registration. Hold a display job before it starts and hold a worker at termination, switch accounts/start a new runtime, then release them: no old alert may adopt the new display epoch or clear the new account’s runtime/alerts. Quit stops delivery without resetting device opt-in.

The native bridge was written against the locked Tauri 2.12.1 source and Apple's [SMAppService documentation](https://developer.apple.com/documentation/servicemanagement/smappservice). These references support implementation choices, not a claim of native runtime verification.
